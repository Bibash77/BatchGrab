# First genuine $5 software purchase: executable experiment

Current measured customers: **0**. Current measured software revenue: **$0**. No outreach or payment collection has been performed. The goal is one genuine paid software customer, then at least one real sale in each following month. A $5 payment exceeds $1 gross revenue for that month; it is not recurring revenue and does not establish profitability.

## The one offer

“Document Handoff: collect this page's accessible documents with reviewed descriptive names, section folders and a source/outcome index. $5 once for the delivered beta version if it helps your real document task.”

Deliver version 0.3.1 ZIP/unpacked files, installation instructions, the verified supported-workflow description and an agreed delivered-version license/receipt. No subscription, license server, AI service or guaranteed lifetime site support. Be explicit that the evaluation build currently exposes the whole workflow without an enforced paid gate. Do not describe it as exclusive or disguise an optional support donation as a software sale. If an unrestricted free copy is sufficient and they decline to buy, record that result.

## The first reachable person

Use one warm introduction to a self-purchasing independent researcher/consultant who is preparing a report, public tender attachment pack or client document folder this week. The owner must choose the introducer; no personal contact list has been accessed. Qualify the **task**, not the title:

- 20–100 legally accessible document links, with labels that identify at least some files better than their URL names.
- A real handoff/filing need and a next batch in the coming month.
- Authority to install a Chrome beta and decide on $5.
- No need for protected Scribd extraction, private uploads, conversion, hidden APIs or a whole-site crawler.

Ask the introducer to forward this draft, rather than sharing someone else's details:

> I made a Chrome beta for collecting web documents into useful filenames and section folders, with a CSV that records sources and what actually downloaded. Could we try it on a current public document batch you are allowed to save? Evaluation is free. If it is useful for your ongoing work, I want to test a $5 one-time license for the delivered version. We will compare it with your existing free tool first; I do not yet know whether mine saves you time.

No warm route: ask a moderator of one relevant professional/VA/research community for permission to share this specific beta invitation, following that community's current rules. Obtain permission before posting; this report does not grant it or claim any community already allows recruitment. Do not cold-message old issue authors or send bulk email. Public issue reports are workflow evidence, not a prospect list.

## Fair trial, 20 minutes

1. Tester chooses 10–20 documents from their current task. First write the intended files and names independently of the extension output; include generic links, duplicate-looking titles and one edited name if present. Do not use our authored demo as customer validation.
2. Use the tester's normal free tool. If SMD is the best alternative, enable its appropriate Link text/title/alt masks and folder settings. Allow learning/setup. Do not compare against deliberately bad defaults.
3. Repeat with Batch Grab on the same subset and page state. Alternate tool order across testers. Time setup, review/corrections, transfer and cleanup separately; record actual UI interactions if useful. Download speed may be server-bound.
4. Verify saved names, directories and content of a sample (and completeness against the independent list). Close the popup during pending jobs, reopen outcomes, and export the index. Record unexpected content separately from Chrome's transfer status.
5. Ask: “Which would you use for your next real batch? For this delivered version, would you pay $5 once rather than continue with the free alternative?” Then request an actual purchase if yes. A polite yes, email signup, referral, invoice sent or a checkout click is not revenue.

A meaningful result is an independently observed reduction in corrections/cleanup without missing files, or a source-index requirement the user actually has. There is no invented minimum savings percentage. Record the user's own threshold and why the free tool is insufficient. Don't lead them to praise the feature.

## Purchase and delivery boundary

Payments and external licensing were explicitly excluded from implementation. No checkout/account has been created. Once an actual buyer asks to proceed, the owner can separately authorize use of an existing legitimate invoice/payment-link provider in the owner's account. Confirm seller eligibility, actual fees, delivery scope and refund terms then. No developer-controlled escrow or new backend is needed for one sale. If no authorized payment route exists, retain an unpaid commitment as such; do not claim success.

After cleared payment, deliver the versioned ZIP and instructions plus receipt for the agreed software license. Offer to refund if it cannot perform the agreed supported task, subject to applicable rights; this is a proposed experimental policy, not a legal guarantee. Count the transaction only as a genuine software purchase when the customer chose it for use, received it and kept it. A founder purchase, supportive tip or fake testimonial does not count.

## Repeat monthly without pretending one-time sales are MRR

After a retained purchase, ask permission for one factual before/after case study and one introduction to a peer with the same job. Each month, offer three new qualified trials through the same permitted route, aiming for one new $5 software buyer. This is an activity plan, **not a conversion forecast**. Do not charge an existing perpetual-version buyer again for the same version. If no new sale occurs that month, the monthly revenue goal is not met even if a long-term average exceeds $1.

Track gross paid, fee, refund, net receipt and support minutes. If routine support approaches 15 minutes per $5 sale, narrow supported tasks or reconsider price; local processing doesn't make founder time free. Do not buy acquisition until actual margins and a repeatable route exist.

## Pass / fail / inconclusive

- **Pass initial experiment:** one independent task-qualified person pays $5 for using the software, receives it, succeeds at the agreed task and keeps the purchase. Then test real repeat use and a new buyer next month.
- **Reject current paid hypothesis:** after three qualified successful trials, nobody buys and users prefer adequate free tools; or the measured workflow advantage disappears. Stop adding paid features. Document the reasons.
- **Fix product first:** missed files, unsafe/wrong outputs or misleading completion on the supported task. Correctness remains free.
- **Inconclusive:** no qualified people, a blocked payment route, installation restrictions, or a task outside scope. Address that bottleneck without claiming proved demand or product rejection.
